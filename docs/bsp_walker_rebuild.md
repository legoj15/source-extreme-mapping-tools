# BSP walker rebuild (`bspwalk`)

Status: milestones 1 to 5 built (#10 to #14); milestone 6 (#15, integration) partly: lmoptimizer and vis_simulator call bspwalk.exe (below), the Python walker is deleted (bspwalk.exe is the only walker; a missing exe is an error, the GUIs expose tiers, threads and extra args) and the tier output policy is decided (#16; see Decisions). Tier B's face and mirror passes have a GPU path (OptiX), the default; `-cpuvis` is the reference, `-vischeck` compares the two (2026-11-05, RTX 3090: 0 disagreements on the 18 fixtures, below). The fan pass is CPU only. Replaces the Python walker (`game/bin/x64/{reachability,visibility,collision,phy_reader}.py`).
Goal: from a compiled BSP, find every face no player can ever see, and do it in minutes on a worst-case map.

## Why a rebuild, not a patch

Measured 2026-11-02 on `unit_test_maps/fightspace3_unittest.bsp` (full ±16384 grid, multi-floor buildings, teleports): the Python reachability flood at 16u did not finish in 15 minutes; the visibility pass never started.

Verified defects in the Python walker (the ones that cause false never-visible, the must-not-happen error):

| Defect | Where | Effect |
|---|---|---|
| PHY vertices read 4 bytes late; one IVP axis is always 0 | `phy_reader.py` vertex_base | Every static prop is a zero-thickness sheet; can't stand on crates/desks. Correct = per-ledge `c_point_offset`, axes `(x, z, -y)` (vphysics ConvertPositionToHL). The "Correct Swizzle" comment in `collision.py:325` is wrong; it only looked right because of the misread. Evidence: parsed PHY bounding boxes vs `.mdl` header hull (offsets 104/116) for fence01a, oildrum001, controlroom_desk001b, lamppost03a_off, furniturecouch001a from `hl2_misc_dir.vpk`. The current code gives one axis exactly 0; vertex_base−4 with `(x, z, −y)` matches all five. |
| Displacements absent from collision | `collision.py` | Displacement terrain is not walkable. |
| Bevel planes skipped in AABB-vs-brush | `_hull_intersects_brush` | Reports solid in open space near angled brushes; flood stops early. |
| Grid clamped to entity-origin bbox ±512u | `_compute_play_bounds` | Areas far from entities never explored. |
| Eyes snapped to cell bottom; XY to cell centre | `grid_to_world` | Eye height wrong by 0–16u; gaps narrower than grid slack missed. |
| No mid-jump eyes; jump reach 3 cells | `run()` jump branch | Faces visible only while jumping, and platforms across >48u gaps, missed. |
| Teleports, water, `func_ladder`, movers not modelled; `func_useableladder` only seeded as discrete cells (no climb volume; the clearance check drops cells near walls) | `run()`, `reachability.py:391-444` | Whole regions unreached. |
| Doors / `func_brush` permanently solid and opaque | `_entity_headnodes` | Rooms behind doors under-flooded and occluded. |
| PVS filter uses only the centroid's cluster | `_worker_check_face` | Faces spanning clusters lose eyes. |
| ~13 samples per face regardless of area; eye list truncated at 2048 | `_face_sample_points`, `MAX_EYES_PER_FACE` | Large partly-hidden faces missed. |
| Prop collision used as a sight occluder | `trace_ray_full` | Chain-link fences hide what's behind them. |

Speed is architectural: per-ray recursive BSP walk in Python, prop ray tests scanning every 64u cell in the ray's AABB, PVS RLE decoded per eye-face pair, BSP re-parsed per worker.

## Shape of the new tool

A native console tool `bspwalk.exe` (C++ / CUDA / OptiX), source in `src/utils/bspwalk/`, binary in `game/bin/x64/`. Same build stack as `vvis_optix`: CUDA from `CUDA_PATH`, 13.2 or newer (13.4 recommended; 13.1's cudafe++ crashes under MSVC 14.51), and clear `NoDefaultCurrentDirectoryInExePath` before MSBuild or the CUDA custom build steps fail.

- **Input:** compiled BSP after VBSP (`-emitsideids`) and VVIS, plus `-game` for model/collision loading.
- **Output:** one JSON per BSP: per face `{face, sideids, tier, reason}` plus run stats. Optional debug outputs: OBJ of C-space, walkable polygons, and eye volume, for viewing in Blender.
- **Python keeps** orchestration and VMF editing (`lmoptimizer.py`, `vis_simulator.py`), which shell out to `bspwalk.exe` and read the JSON.

Reuse, don't re-derive:
- BSP loading: `src/utils/common/bsplib.cpp/.h` (`LoadBSPFile`, dbrushes/brushsides/planes/leafs/leaffaces/dispinfo/entities). Static props come from the game lump, read the way `CVradStaticPropMgr::UnserializeStaticProps()` does (`vradstaticprops.cpp:285`).
- Prop collision: vphysics via the same path VRAD uses (`vradstaticprops.cpp:1177` `VCollideLoad`, convex access). No hand-parsed PHY. This covers `prop_static` (game lump) **and** entity-lump models: `prop_physics*`, `prop_dynamic*`, `func_pushable`, at their spawn origin/angles. Entity props count as solid for standing on (over-reach, safe) and never as sight occluders (they move or break).
- Displacement collision triangles: VBSP/VRAD displacement builders (`disp_ivp.cpp` shows the triangle source). `DispFaceProblem` (`bsplib.h`, shared with VRAD) checks the lumps first: dispinfo index, power 2..4, vert and tri ranges, the face's 4 surfedges, the edges, vertices and texinfo they name. A displacement that fails is skipped with a warning naming its dispinfo and face (`bw_disp.cpp`), and has no collision triangles. Stage 5 never evaluates its face, or any face with fewer than 3 edges or with surfedge, edge or vertex indices out of range: always visible (reason `bad_lump`, counted in `vis.bad_lump_faces`; a brush entity face keeps `brush_entity`). VRAD gives such a displacement no collision tree and no lightmap, and lights a face whose dispinfo index is outside the lump as a plain face (in both face lumps).
- Polygon clipping: the algorithms of `src/utils/common/polylib.cpp` (`ChopWinding`/`ClipWindingEpsilon`). polylib itself is single precision (`vec_t` = float), so bspwalk carries a double-precision copy of the few winding functions it needs. In float, a 0.01u sliver near ±16384 is only ~5 ULP wide.
- OptiX: a small dedicated module modelled on `vvis_optix.cpp/.cu` (~600 lines). Not `RayTraceOptiX`, which is a VRAD-coupled static singleton.

## Stage 1: collision world in configuration space

The player is an axis-aligned box that never rotates, so collision reduces exactly to a point against obstacles grown by the box (Minkowski sum). For a feet-origin point the box is `[-16,16]×[-16,16]×[0,72]` standing and `[0,36]` crouched (from the game profile, below).

- Every solid convex (world brush, solid brush entity per policy, prop convex, displacement triangle) is grown into a convex polytope. Its planes are: the source face planes pushed out by the box support, the 6 axial planes, and the edge×axis bevels. This is exact, which is what the bevel-skipping Python test was not.
- Contents filtering uses the player mask (SOLID, PLAYERCLIP, MOVEABLE, WINDOW, GRATE), with no ad-hoc class list.
- Every grown polytope is at least 32u wide horizontally, so a thin wall can never be tunnelled through. Gaps between obstacles, slivers included, stay as exact free space.

Debug output: grown solids as OBJ.

How Stages 2 and 3 work (`bw_walk.cpp`, milestone 3, #12):
- **Up faces.** The crouch-grown face polygons with n.z ≥ 0.7 (0.7 is `WALK_MIN_NZ`) of every grown category, plus those of each `tops_only` mover pose. Up faces are the same for both postures (for n.z > 0 the support of −B lies on its z = 0 face, which does not depend on the hull height), so nodes are crouch polygons; each node also carries its stand sub-polygons (`stand_count`, `stand_area`), the parts free of the stand-grown obstacles. Nothing is derived from plane triples: only face polygons and planes as half-spaces.
- **Subtraction.** Each up face is chopped at the 64u grid lines (`WALK_CHOP`, X then Y), then every piece has the other obstacles of the same posture subtracted: a quick "does the polygon reach the interior" test (separating plane, then a Sutherland-Hodgman clip), then a peel, one plane at a time, of the parts in front of each plane. Clippers are shrunk by 1/32u (`d -= 1/32`, `WALK_SHRINK`), the safe direction. A polytope never clips its own face. Only `CategoryIsObstacle` polytopes clip; `entity_prop` and mover tops never clip. Slivers are kept: a piece is dropped only when its area is 0 at 1e-9 of its extent squared. The spatial index is a hierarchical XY hash (cell 64·4^L, 9 levels, each polytope at the finest level where it spans at most about 3 cells).
- **Coplanar dedupe.** Two obstacles that share a coplanar up face region (a brush on a brush of the same height, both grown 16u past their edges) would give the same floor twice, since a shrunk clipper never removes the other's coplanar top. The lower obstacle index keeps the shared region: the higher one subtracts the lower one's face prism (its edge planes plus a ±1u slab). This is exact, because the region is clipped by the same obstacles either way.
- **Poses** (`tops_only` only, grown with the crouch hull at each pose; their up faces, which are the same for both hulls, are clipped by world obstacles; #13 adds the stand grow if ride edges need it). Poses are computed once per entity: spawn; `func_door` open at `movedir · (|movedir · size| − lip)` (`doors.cpp`; `size` is the dmodels size, which equals the engine's `OBBSize − 2`); `func_door_rotating` at `angles ± axis · distance` about the entity origin (spawnflag 2 reverses, 64 = roll, 128 = pitch, `distance` defaults to 90; a yaw door that is not one-way, spawnflag 16, gets both signs because it opens away from the player); `func_movelinear` at `origin − movedir · MoveDistance · StartPosition` and that plus `movedir · MoveDistance` (`func_movelinear.cpp`; a missing `MoveDistance` falls back to the door travel). Each node carries `category`, `convex` and `pose` (0 = spawn).
- **Train poses and parents (#13 phase B).** `func_tracktrain` / `func_tanktrain`: one pose per `path_track` reachable from its `target` through `target` and `altpath`, origin = path origin + (0, 0, `height`) (`trains.cpp` `CFuncTrackTrain::Find`); `func_train`: one per `path_corner`, model centre at the corner (`CFuncTrain::Activate`). Rotation (`orientationtype`) is ignored: poses are translations. At most 256 poses; a path node whose translation is zero is the spawn pose. An entity with a `parentname` takes its root mover's poses (up to 16 levels) when the root moves. Each mover entity also keeps its pose links (`MoverEntity`): doors spawn ↔ each open pose, `func_movelinear` every pair, trains spawn → first path node and every path link (so a looping path links last → first). The swept volume between poses (for the eye volume) is #14's.
- **Edges.** For each node pair whose XY bounds touch, take the parts of A's boundary inside B's XY projection (expanded 1e-4u) and of B's inside A's: sub-segments P(s) = P0 + s (P1 − P0), s in [0, 1]. Along one, both planes are linear in s, so dz(s) = zB − zA is linear and each kind's dz band is an exact s-interval: `|dz| ≤ 18` (`PlayerProfile::stepHeight`) is a two-way walk edge; `18 ≤ dz ≤ 57.33` (`maxJumpRise`, derived from the profile: apex v²/2g = 21.33 at 160 u/s, plus the 36 crouch lift; 57 before #13) a jump-up edge from the lower node; `dz ≥ 18` the drop edge from the higher one (band ends closed: that only adds edges, and walk wins anyway). The blocked parameters for one shrunk crouch obstacle are the s-projection of (the vertical region swept between A and B over the sub-segment) ∩ (the polytope): split at the s where zA and zB cross, each piece is a convex quad in (s, z), clipped by the polytope's planes (tolerance `FREE_TOL` in the planes, so touching is free), and its s-range is one closed interval. A kind holds where its band meets the free set (the sub-segment minus the union of those intervals), or where `|dz| ≤ 1e-6` (the surfaces meet). Speed: every sub-segment's ends and midpoint are tried first against the point test (a subset of the exact answer); the exact pass then runs only for kinds still missing, only over the span of their bands, and stops as soon as one obstacle (the last blocker first) covers that span. A pair with any walk gets only the walk edge. Known answers in `-selftest` (e): a flat floor meeting a slope whose step band lies strictly between the samples gets a walk edge; a 100u drop whose samples are all blocked gets its drop edge through the gap between two slabs; one slab over the whole boundary gives no edge. Both of the first two failed against the sampled version.
- **Off-map polygons (#21).** A walkable polygon whose probes, its vertex centroid and each vertex pulled 1u toward it, all lie 1u up in a leaf of cluster -1 is dropped before the stand pass. A feet point just above a reachable floor is inside the player box and so never in a solid leaf: such a polygon is outside the sealed map (the top of its outer shell, a roof above a skybox) and no player stands on it. Nothing is culled when no leaf has a cluster, or with `-keepoffmap`. CS:S maps, `-noarcs`: cs_office 122,990 -> 102,139 nodes (-17%), cs_italy 30,300 -> 22,689 (-25%), de_dust 146,024 -> 123,877 (-15%; area 154M -> 75M u^2); the reached set is the same node for node in count and area on all three, and the 17 fixtures then built are unchanged. de_dust's JSON: 63 MB, 52 MB culled, 34 MB with `-reachslim` as well. fightspace3 (the outer shell above z 12288 alone was 247k unreached nodes) is not measured on this box.

How #13 arcs work (`bw_arcs.cpp/.h`, `bw_arcs.cu`, `bw_optix.cpp`, phase A: horizontal jumps and falls):
- **Rounds, target-driven.** Round 0 is the CPU BFS. Each later round pairs every launch node (rim or slope, below) reached since the previous round (A) with every unreached node (B) whose XY box is within R(drop) of A's (below) and whose lowest point is at most `maxJumpRise` above A's highest. It traces each pair's arcs, adds an `arc` edge A → B for the first free one, and continues the BFS. A node is a launch node in one round, except a surf slide the flood later made fresh or gave a higher cap, which launches again; the rounds stop when one reaches nothing (when every node is reached, the round's trigger targets still run). Inside a round the launch nodes go in chunks of 16384, each chunk's pairs are made 2048 launch nodes at a time (`ARC_SUB_A`) and traced in batches of 1M (`ARC_PAIR_BATCH`) as they fill, so a later sub-chunk skips targets an earlier one reached and the pair list holds at most one sub-chunk plus a partial batch (#26: de_aztec builds up to 152M pairs a chunk; peak 6,455 MB before, 3,108 MB after, the same nodes reached), and each batch in 9 tiers, one per launch/landing combination. A pair's geometry (launch and landing points) is computed once per batch and shared by its tiers. After each tier the BFS runs, and pairs whose B is now reached, by any earlier tier, batch or chunk of the round, are dropped (this changes the arc count, not what is reached).
- **Launch nodes: rim and slope.** A rim node launches arcs: part of its boundary has no walk-edge neighbour covering it in XY, or only one more than 0.1u lower there, a step down (`ComputeRimNodes`, the same boundary sub-segments as the edge pass, gaps over 1e-3u). A flat interior node does not: its arcs first cross a neighbour at the same height, which launches the same family. A sloped interior node launches only toward targets in its downhill half-plane whose drop is small enough (`SlopeLaunchDrop`). To first order, launching dh lower loses dh × vmax / v_fall of reach (v_fall the landing fall speed), and a step dx downhill is dx × tan(slope) lower. So the uphill node beats its downhill neighbour only when tan(slope) × vmax > v_fall, that is for drops up to (tan(slope) × vmax / 0.75)² / 2g − `maxJumpRise` (0.75 is slack for the first-order argument). These are hillside jumps across a valley or ditch onto something the lower slope cannot reach. Both rules are heuristics, measured on fightspace3 against `-arcallnodes` (below). fightspace3 has 92,437 rim nodes and 635,786 slope launchers of 1,801,694 nodes.
- **R depends on the drop.** R(dz) = `max_air_speed × reach_margin × t(dz) + 2 × half_width`, where t(dz) is a duck-jump's time to land dz below its launch height (with air jumps, each at the apex), dz clamped to [0, `arc_max_drop`]. A pair uses the largest drop between the boxes (A's top to B's bottom). The hash is queried with R(`arc_max_drop`). hl2: R(0) = 736 u/s × 0.7038 s + 32 = 550u, and R(730.5) = 1421u. `arc_max_drop` is the fatal fall for hl2 and episodic (PLAYER_FATAL_FALL_SPEED 922.5, `game/shared/shareddefs.h:370`: v²/2g plus the jump apex, 730.5u; CHalfLife2 is a CSingleplayRules, `hl2_gamerules.h:31`, whose fall damage grows with speed, `singleplay_gamerules.cpp:289-290`). hl2mp has no fatal fall: CHL2MPRules is a CMultiplayRules, which deals a fixed 10 damage while `mp_falldamage` is 0 (`multiplay_gamerules.cpp:619-631`, default "0" at `game.cpp:34`), so it uses 1024u like cstrike and tf (those two unverified). Accepted limitation: a target farther than R(`arc_max_drop`) in XY is never tried, even when it lies deeper and a longer fall could reach it. For hl2 and episodic such a fall is fatal anyway. Such targets show up in the unreached-but-walkable report.
- **The arc family of a pair.** Launch points on A: L0 the point of A nearest B (closest pair of the two polygons), L1 A's boundary point nearest B's centroid, L2 A's boundary point nearest B's far vertex. Landing points on B: T0 nearest A, T1 the centroid, T2 the vertex farthest from L0. Jump launches and landings are moved 0.25u toward their polygon's centroid (`ARC_INSET`; at most half way), since an edge cut by an obstacle lies 1/32u inside it. Walk-offs start on the exact edge point. Combinations in tier order: (0,0) (0,1) (1,1) (0,2) (2,2) (1,0) (1,2) (2,0) (2,1); a repeat of an earlier one's points is skipped. Kinds per combination: a duck-jump (feet lifted by `crouch_lift` at launch, crouch mesh), a crouched jump (no lift, crouch mesh), and a walk-off (vz = 0, crouch mesh, only when B is lower); with `air_jumps` 1 both jumps are also tried with a second jump at the apex. A standing jump is not generated: its trajectory equals the crouched jump's with a taller hull, so whenever it is free the crouched jump is too. Each arc lands exactly on its point, on the descending branch; one that needs more horizontal speed than `max_air_speed × reach_margin` is dropped.
- **Tracing.** An arc is traced as chords of equal time, each at most dt = sqrt(8 · `ARC_SAGITTA` / g) long (sagitta g dt²/8 ≤ 1u), against the grown obstacles (`CategoryIsObstacle` only) of its posture. Every arc is lifted 1/32u (`ARC_LIFT`; start and landing both) and traced over its full length: rays see an obstacle only where they cross a face, so any tolerance window at an end would hide that end's crossing. Interior chord joints overlap by 1/64u, so a face crossed exactly at a joint lies strictly inside one ray. A chord lies on or below the parabola between its ends (the parabola bulges above it by at most the sagitta s = g dt²/8 at mid-chord), so unraised chords err one way only: they can hit a floor the true arc clears, and miss an overhang it grazes from below. Every chord is therefore raised by half the largest sagitta of its arc (`ArcTraceRaise`, g dt_max²/16, the same on both paths: the CPU chords and the GPU origin), which bounds the traced path to ±s/2 ≤ ±0.5u of the true one instead of 0 to −s, with one raise per arc so the joints stay continuous. A fully one-sided-safe trace has no cheap form with rays: two rays bounding the band can both miss an obstacle corner poking between them, and halving the error costs about 1.41× the chords. An arc whose traced (raised) start is not at least 1/128u (`ARC_START_CLEAR`) outside every obstacle is not tried on either path, because a ray starting inside or on a face can miss its exit or entry. It is tested per arc against the crouch obstacles whose boxes meet the launch node's box (raised by `crouch_lift` plus half `ARC_SAGITTA`), listed once per launch node. The tracers hold at most `ARC_MAX_CHORDS` (1024) chords an arc; a profile whose top-to-bottom fall of the ±16384 world needs more (a tiny gravity or a huge jump velocity) is refused at load, so no arc is ever truncated. Phase A traces every arc crouched, so only the crouch obstacle set and GAS are built (`mesh_tris` and `gas_mb` stand are 0). GPU: OptiX, one launch per tier, one thread per arc, `TERMINATE_ON_FIRST_HIT | DISABLE_ANYHIT | DISABLE_CLOSESTHIT` (the miss program clears the payload), and one compacted GAS (crouch; fan-triangulated face polygons, whose vertices are exact sum points; the stand mesh is not built, phase B included, since every arc is traced crouched). CPU reference (`-cpuarcs`, or no CUDA/OptiX/PTX): the same chords clipped against each candidate polytope's planes in double, blocked only ARC_TOUCH (1e-6) inside. `-arccheck` traces both and floods on the CPU result. It first runs a GPU-only flood from the same round-0 state and reports the nodes only one of the two floods reaches (a CPU-only node is a warning naming up to 5 of them). A disagreement is explained when its grazing depth (a ternary search of max_t min_k (d_k − n_k · x(t)) over the chords) is at most 1/64u (`ARC_FLOAT_BOUND`, float rounding at |coord| ≤ 2^15). An unexplained one exits 1.

- **Slides and conveyors (phase B).** Slide nodes launch walk-offs only (no jumps, no air jumps), only toward targets whose lowest point is below the slide's highest, and are always launch nodes; surfable slides also launch surf arcs (#24, "Surfing" below). A `func_conveyor` node's speed is added to the air speed of its arcs and widens its R by the same ratio; its surf arcs use the same raised speed for their vz, apex and reach, without the ratio.

How #13 special movement works (`bw_special.cpp`, `bw_walk.cpp`, `bw_arcs.cpp`, phase B). Each special thing is a flood vertex after the nodes (flood id = node count + index) with directed edges to nodes and to other special vertices; the BFS runs over them like over nodes. Some carry a launcher: velocity-driven arcs that run in the arc rounds. Every touch test adds 1e-3u to the polytope planes, and an obstacle that hides an overlap is shrunk by 1/32u, so rounding only over-reaches.
- **Water.** A `CONTENTS_WATER` or `CONTENTS_SLIME` world brush that does not block the player is category `water`: grown like the others but never an obstacle. Its crouch-grown volume is a vertex of free 3-D movement, joined both ways to every node whose polygon touches it, and to every other water volume it overlaps unless the overlap lies inside one (shrunk) crouch obstacle (two pools either side of a wall). Its top faces are ordinary walk nodes (surface nodes), so climbing out (walk), jumping out up to `max_jump_rise` above the surface with a free path (the edge pass's jump edge), and falling in from above (drop and arc edges) need nothing else. Selftest (g5): a surface node gets a jump edge to a ledge 57u above the surface and none to one 58u above. Limitation: water in brush entities (`func_water_analog`) is not water; `CheckWaterJump`'s 256 u/s exit is covered by the jump rise only up to 57.33u; a stacked water brush's top face inside other water is also a "surface" node (over-reach).
- **func_useableladder.** The segment between `point0` and `point1` (absolute positions, the lower one the bottom; spawnflag 1, a fake ladder, is skipped). A node mounts it, and the climber can leave to it, when its polygon comes within 64u (`FindLadder`) of the segment swept down by `max_jump_rise` (a jump to reach the ladder). Each `info_ladder_dismount` within 100u of the segment, untargeted or targeting the ladder, gets an edge from the ladder to the node it falls to. The launcher samples the segment every 16u. Limitation: no line-of-sight test for the mount (a ladder behind a thin wall over-reaches).
- **Ladder brushes.** `CONTENTS_LADDER` brushes of the world (vbsp moves `func_ladder` there), widened 2u (`LadderMove`'s trace), then grown by the stand hull: the climb volume. Nodes touching it swept down by `max_jump_rise` join it both ways. The launcher samples its side faces on a 16u grid (at most 2048 points).
- **Ladder launch families:** let go (vz 0, full air speed), the ladder's own jump (vz up to 250, at most 270 u/s across: a brush ladder pushes off at 270 along its normal, a useable ladder jumps 200 along the view plus 50 up), and a normal jump and duck-jump at full air speed.
- **Why the ladder jump keeps 270 across, not `max_air_speed`.** Air strafing cannot add much during one ladder jump. `CGameMovement::AirAccelerate` (`gamemovement.cpp:1707-1747`) caps the wish speed at `GetAirSpeedCap()`, 30 u/s (`gamemovement.h:104`), and adds speed only along the wish direction up to that cap. Turning the wish direction every tick (a perfect strafe) adds at most 30 u/s of perpendicular speed per tick, so after n ticks the speed is at most sqrt(270² + n · 30²). The family's 250 u/s jump lands back at its height after 2 · 250 / 600 = 0.833 s, which is 55 ticks at 66 tick: at most sqrt(270² + 55 · 30²) ≈ 350 u/s, a range of at most 292u. The arc's 270 u/s gives 225u. The difference is 67u, and it applies only to the ladder's own jump. The let-go, jump and duck-jump families already fly at the full `max_air_speed` (736 u/s), which covers any strafed route from a ladder. Giving the ladder jump 736 u/s as well made f09's hut 2, seen only through a 604u gap, reachable at 613u, which no strafe reaches.
- **Triggers.** `trigger_push`, `trigger_catapult` and `trigger_teleport` whose spawnflags let players fire them (1 clients or 64 everything; others are counted in `skipped_non_player_triggers`). `StartDisabled` ones count, since an output may enable them. Their model brushes (any contents, entity transform) grown by the stand hull are the volume; the volume swept down by `max_jump_rise` is the touch shape: a node whose polygon touches it fires the trigger (the standing box, raised by at most a jump, enters the brush). A trigger delivers the player nowhere by itself: a teleport delivers through its arrivals, a push or catapult through its launch arcs. Water and ladder volumes that overlap a touch shape fire it. A trigger crossed only in flight fires too (trigger targets, below).
- **Trigger targets.** Points sampled inside each trigger volume (a grid 32u apart, coarser until at most 256 per volume, plus the volume's centroid; pushes 64u and 64) are arc targets. Each round, every launch node of the round pairs with each target whose vertex is unreached under the node pairs' rules (at most `max_jump_rise` above the node's top, within R(drop) in XY). Launch points are the node's boundary point nearest the target (exact for the walk-off, inset for the jumps) and, when the target lies above the node, the node's point right below it. The families are the duck-jump, the jump (with `air_jumps`, also with a second jump at the apex) and the walk-off (downward only). A slide walks off, and a surf slide also launches its surf arcs, under the same speed, apex and reach as its node pairs (Surfing, below). The arc ends at the target and is traced up to there. A free arc reaches the target's vertex: the teleport or catapult, or that point's push entry.
- **trigger_push.** Velocity `PushVelocity` = AngleVectors(`pushdir`) × `speed` (0 means 100; world space, `CTriggerPush::Spawn`). A continuous push sets base velocity on every touch (`triggers.cpp` `CTriggerPush::Touch`). Its z part acts as an acceleration: `StartGravity` (`gamemovement.cpp:1255-1265`) adds `basevel.z · dt` to the velocity each tick and clears it, so inside the push gravity is g − s·dir.z. Its xy part is added for every move and kept as momentum when the player leaves (`player_command.cpp:115-120`). A lifting push (dir.z > 0) also takes a standing player off the ground. The push acts only on a player inside it, from the state he enters with, so it is reached through **push entries**. Each entry is a flood vertex with a launcher that flies from where the push takes the player:
  - *node entries*: one per cluster of nodes touching the touch shape, a 256u XY cell and a 64u band of the node's lowest z. It launches from the nodes' parts under the push (their vertices moved 0.25u inward, and their centroids), keeping one point per 32u cell, at most 48 (`PUSH_CLUSTER_*`). Every node of the cluster has an edge to the entry, not to the push, so the entry fires when its first node is reached and launches from all of them: over-reach only. One entry per node gave fightspace3 62,283 entries (its river and water pushes touch tens of thousands of nodes) and 233 s of special launches; clusters give 3,272 entries, 16.5 s and the same reached set.
  - *point entries*: one per trigger target point inside the push, reached by a free arc to the point.
  - *overlaps*: where a water volume, a useable ladder segment or a ladder brush's climb volume meets the push. The water or ladder vertex has an edge to the entry.

  The push vertex only counts as reached, through an edge from each of its entries. The entry state is standing (vz 0), jumping (vj) or duck-jumping (lifted `crouch_lift`). The flight (`SolvePushArc`, selftest (g2b)) is under gravity gIn = min(g, g − s·dir.z) up to the volume's top, or to the apex under gIn when gIn > 0, and then ballistic under g down to the landing. The same flight exiting half way up is also tried, and the whole flight inside the push when gIn > 0. A push pulling down uses plain g (more reach). A launcher whose families all carry the same horizontal push velocity b pairs only with nodes within its own-speed reach (`max_air_speed` × flight time, plus the hull) of its box swept along b·t (`sweepT`, `sweepOwn`): the capsule the horizontal check allows, bounded through the box centres and half diagonals. The horizontal velocity stays constant through the flight, and lies within `max_air_speed` of some point of the segment from 0 to s·dir.xy: the push may carry the player for part of the flight or all of it. Both tracers follow the two-piece flight: piece 0 under g + `dg0` (a curve upward when gIn < 0), then plain gravity after `tKick`. With an upward-curving piece both pieces take half the sagitta bound, and the chords are raised by (down − up)/2 of the two largest sagittas, so every point stays within `ARC_SAGITTA`/2 of its chord. `SF_TRIG_PUSH_ONCE` (0x80) is one impulse added to the entry state: plain flights at vz s·dir.z and vj + s·dir.z (and a duck-jump), with base s·dir.xy. f14's push is 900 straight up at gravity 600: the net upward acceleration is 300 u/s², so a player standing in the column leaves its top (feet z 224) at sqrt(2 · 300 · 224) = 366.6 u/s and peaks at 336 over the 160u ledge. Speed 600 only cancels gravity, so a standing player hovers, while a jumping player keeps rising at 160 u/s and still makes the ledge. Chamber W's push of 300 leaves gravity 300 inside, so a duck-jump peaks at 36 + 160²/600 = 78.7u and ledge W stays unreached: the negative control. Scratch compiles of f14 (2026-11-03) give these results for ledge P and its hut. Removing the push, or turning it horizontal (`pushdir 0 270 0` at 900): both unreached. Speed 600: reached, through the jump family. A push-once of 600: reached. Raising chamber W's push to 900 reaches ledge W. With `-noarcs` ledge P is not reached (the push now acts only through its launches). Limitations: one horizontal velocity for the whole flight, where a real player can rise first and drift after; exits sampled at the top and half way; a launcher fires once, when its entry is first reached; `trigger_wind` is not modelled.
- **trigger_catapult** (later engines, best effort): `playerSpeed` along `launchDirection` as one launcher family, plus an edge to the node `launchTarget` falls to.
- **trigger_teleport.** Every entity whose targetname matches `target` (the engine takes the first match; this takes all) is a destination: an arrival vertex with an edge to the node the destination origin falls to (any depth; an unmapped destination warns) and to any water volume containing it, and a point launcher (walk-off, jump and duck-jump at full air speed: HL2 keeps the player's velocity). With a `landmark`, the trigger's volumes moved by (destination − landmark) are arrival regions too (the arrival is offset by the player's offset from the landmark): their touching nodes get edges, and their boundary launches. Selftest has no teleport case; f08 covers it.
- **Rides.** One vertex per (root mover, pose) for movers with at least two poses. Every `tops_only` node of an entity riding that root at that pose joins it both ways, and the root's pose links join its vertices both ways: a rider moves with the platform to every linked pose and steps off there. Selftest (g3): track-train and func_train pose translations.
- **Slides.** Faces with 0.1 ≤ n.z < 0.7 (`SLIDE_MIN_NZ`; water excluded) are slide nodes: a landing for drops, arcs and walk edges, never a jump launch. A walk-height boundary with a slide is an `EDGE_SLIDE`. It always runs onto the slide. It runs off the slide where the player crosses: across the slide's boundary edge lying in the other node (along its outward normal), or across the other node's edge lying in the slide (against its outward normal). One such crossing longer than 1/100u that is at most 30° uphill of the slide's contour line is enough (`SlideExitAllowed`), and the downhill direction is the plane's gradient, the XY part of its normal. With only a corner contact, the direction from the slide's centroid to the contact decides. The earlier test used the step between the two polygons' vertex centroids, which could call a legal sideways exit uphill: a thin slide sliver beside a full cell has its centroid low, so the cell's centroid sits more than 30° uphill of it. A pair with a slide takes every flag, not just the first walk, so its drop edges are kept next to the one-way slide edges. Faces steeper than n.z 0.1 are walls (a fall along one moves at most 0.1 of its drop sideways). Surfing is below.
- **Vehicles.** `prop_vehicle_*` origins are always seeds (`vehicle: true`), by policy: a player can always reach a vehicle's spawn to board it. Driving is not simulated. `-vehicle-free` only adds the both-way traversal: it floods from those seeds over walk, jump, drop and slide edges in both directions before the normal BFS.
- **Special launches.** In each arc round, every special vertex reached since the last round that has a launcher pairs with each unreached node within its reach and below its highest flight point. The reach is the farthest flight of its families from the top of its launch box down to `arc_max_drop` below its bottom; push families use their two-piece flight, and the reach is capped at 262,144u for a barely lifting push. The landing points are the same three a node pair uses: T0, B's boundary point nearest the launcher (inset); T1, B's centroid; and T2, B's vertex farthest from the launcher (inset). The launch points of point launchers are the point nearest each landing point, plus the highest. Volume launchers use the boundary point nearest each landing point and the nearest on a face toward the exit direction. Every launch point is tried with every landing point, and each combination with each family. A plain family with `apexVz` may leave at any vz up to its own, so the vz peaking at the landing height, 0, and the vz whose flight time carries the base velocity to the landing are tried too. `SolveArcBase` solves the exact landing on the descending branch, with horizontal velocity within `hmax` of the family's base (selftest (g2)). Push families use `SolvePushArc` (above). Arcs are generated into per-thread lists and gathered, in batches of 64k pairs, so memory follows the arcs that pairs actually have; the old fixed 48 slots a pair would have been 4.4 GB for a 1M-pair batch. Start clearance, lift and tracing (GPU, CPU, `-arccheck`) are as for node arcs. The first free arc reaches B; no `WalkEdge` is stored for it. A round that reaches only special vertices (a trigger target) still runs another round, so their launchers fire.
- **Surfing (#24, default on; `-nosurf` restores the model above).** A player who reaches a slide with speed rides it along its plane instead of sliding down. The speed is bounded by vmax = `max_air_speed` x `reach_margin` (hl2 736 u/s, the bunny-hop ceiling), so the rise is at most `SurfRise` = vmax^2 / 2g (hl2 451u). Two parts. *Surf moves* (the flood, `bw_walk.cpp` `CWalkFlood`): a slide node reached other than by surfing (a seed, an arc landing, a special vertex, a walk or drop edge from a floor) has moves to every slide of its connected slide surface (slide-slide adjacency from any edge either way), and to every non-slide node at that surface's edges the surface can leave onto (a drop or jump edge only from its slide end, so a drop onto the surface is no way up; a slide edge either way: f18's flat strip at the ramp top is reached through a reversed one, and one-way slide exits lose 64 f18 and 120 f19 nodes with `-noarcs`), whose lowest point is at most `SurfRise` above its own top, through slides no higher than that. There is no XY bound: a surfer can follow a ramp's contour without losing height. (The first version had one, measured from the slide's box centre; review found both problems.) A BFS that already covered a slide with at least as high a cap makes that slide's own BFS redundant, so it is skipped. Surf BFSes wait until the walk queue drains and run highest slide first (`m_SurfHeap`, by top z), so high caps usually cover low ones (a higher slide found later can still run after a lower one): the same reached sets as first-in-first-out, and fewer nodes first reached by a surf move (cs_office 798 -> 128, de_dust 706 -> 1). Until #26 the surface flag was cleared inside the surface loop, so only each surface's first slide surfed (fixing it: f18 +29 nodes, f19 +64, de_dust +2). A node reached by a surf move does not surf again, and that state carries along slide-to-slide edges (a floor resets it): on a slide the player cannot stop to gain speed, so stepping down onto a neighbouring slide must not buy a fresh climb, or chains would climb any cliff. A node first reached fresh after a surf reach runs its edges and surf moves again. *Surf arcs* (`bw_arcs.cpp`): a slide launches, besides its walk-offs, arcs at speed v (`SurfLaunchSpeed`): vmax plus any conveyor speed when the slide was reached fresh, and min(vmax, sqrt(2g (cap - z))) when only by surfing, the energy its surf cap leaves at launch height z, so a surf arc cannot climb past the cap it was surfed under. Their vertical speed is v x sqrt(1 - n.z^2) (the in-plane speed's vertical part) and the one that peaks 1u above the landing when lower, horizontal speed up to vmax (a superset of the in-plane velocities), toward targets up to that speed's apex above it (svz^2 / 2g instead of `max_jump_rise`) and within the matching reach. An arc landing on a slide reached only by surfing is a live target (it makes the slide fresh), and the slides the flood made fresh or raised the cap of launch again next round. A slide reached from a surfed slide without regaining speed (a slide-to-slide walk or drop) takes that slide's cap for its surf arcs if higher and if its bottom is within it (`m_Cap`; the surf BFS skip test keeps its own `m_SurfCap`, the caps of the BFSes that covered the slide). Trigger targets: a surf slide launches the same surf arcs (at the energy rule above) (speed, apex, reach). How #14 visibility works (`bw_eyes.cpp` Stage 4, `bw_vis.cpp` Stage 5, milestone 5):
- **Eye pieces.** The eye volume is a list of convex pieces in world space: polyhedra (planes `n . x <= d` with their vertices), segments and points. Each is split down the world BSP to the leaves it touches (a polyhedron straddling a node plane is cut in two; a side that does not build, a sliver, takes the whole piece, which only adds clusters); every leaf's cluster is an eye cluster. Each piece is also sampled for tier B (its vertices, plus world-aligned vertical lines `-eyespacing` apart with points at both ends of each line's span and every spacing between), and the samples are deduplicated. A polyhedron is built from its planes by clipping each plane's base winding by the others; a plane that bounds anything stays however small its face is, and a set whose vertices reach the base winding (open) or with fewer than four faces of area 1e-9 is no piece. The first version dropped small faces: the sides of a subtraction sliver went, the sliver became an open slab, and f09 got 474M samples and 4 bogus eye clusters (134 s); the open test is now in `-selftest` (h5). An eye cluster that pieces touch but no kept sample lies in (a piece that only grazes a thin leaf, missing every vertex and lattice point) is a **bare eye cluster**: the build keeps the box of every piece part in it, and counts them in `eyes.bare_clusters`. No ray can start from such a cluster, so tier B keeps the faces it may see visible (see "Faces kept visible without a ray test").
- **Node columns.** Over each reached node: the free crouch-feet column, the prism from the node's plane up `rise` along z (n . x <= d + rise n.z, so a ramp's prism follows the ramp), minus, for each crouch obstacle (shrunk 1/32u, `CategoryIsObstacle`), the upward extrusion of (obstacle n prism), the hull of its vertices and the same raised past the prism top. That is exact for a column: the prism is a union of vertical segments from its floor, so a prism point lies at or above an obstacle point exactly when the point below it on that segment is in obstacle n prism. An obstacle under the floor (the node's own solid, a coplanar neighbour) meets the prism nowhere and removes nothing; a ceiling or overhang cuts the column at its underside, and nothing past it survives (a void room above a low ceiling stays out). The eye pieces are the feet pieces raised by `eye_crouch`. `rise` = max(`max_jump_rise`, `jump_apex` (1 + `air_jumps`) + `eye_stand` - `eye_crouch`), with `max_jump_rise` = `jump_apex` (1 + `air_jumps`) + `crouch_lift`: the second term wins when a standing jump lifts the eye higher. The eye z therefore runs from feet + `eye_crouch` to feet + `eye_crouch` + `rise`; for hl2 both terms are 57.33, so the top is 28 + 57.33 = 85.33. A standing eye is inside this column when `eye_stand` - `eye_crouch` <= `stand_height` - `crouch_height` (hl2: 36 and 36): a standing box at feet f + t (t up to the jump apex) then contains the crouch box at f + 36 + t and every crouch box between, so its eye f + 64 + t is a crouch eye of the column. When it is not (tf: 23 against 20, unverified profile values), a ceiling just over a standing head would cut the crouch column below that player's eye, so each node also gets a stand-feet column of height `rise` - (`eye_stand` - `eye_crouch`), clipped by the stand-grown obstacles and raised by `eye_stand`, which reaches the same eye top. A node that is the landing of a reached drop edge gets `rise` up to the drop's start height plus the base rise: the fall column over it. A node with no crouch column piece is covered in one of two ways. A sliver whose prism does not build gets the hull of its corner segments from the dead-view height to the column top (thickened by 1/32u when flat), ignoring obstacles (over-reach); like any piece it is ride-swept. A node whose obstacles removed the whole column keeps its dead-view prism (a profile with `eye_crouch` of 14u or less has no such prism and gets the crouch-eye polygon instead). Both cases also get the vertical corner segments, dead view to top: a thin hull is sampled only at its vertices, so the segments are what put samples at every height, and an empty column can also come from a failed clip. Selftest (h1 to h3): a slab over half a floor cuts that half at its shrunk underside and nothing above it, a ceiling at z 20 caps the column, one at z 60 changes nothing, a ramp's column follows the ramp, and the floor's own solid and a wall touching the edge remove nothing.
- **Other pieces.** Water and ladder brushes: each reached volume (crouch-grown water, stand-grown climb volume) as the hull of the volume raised by `eye_crouch` and by `eye_stand`. Obstacles inside are not subtracted: an eye inside a lake bed only over-reaches (a solid leaf adds no cluster, and a ray from inside an occluder is blocked at once). The first version subtracted them, and de_aztec's lake beds (displacement triangles) cut its 12 water volumes into 293k pieces (120 s for the eyes, and 30M samples). Useable ladders: the segment at both eye heights. Arcs: the first free arc of every arc edge, special launch and trigger target join is kept (`WalkGraph::freeArcs`, in the GPU form, so the GPU and CPU paths record the same arcs), and each of its chords is a segment at the crouch eye (every arc is traced crouched). Surf flights (#26, source `surf`, `eye_surf_<n>` in `-dumpobj`): `WalkGraph::surfEyes`, the free part of each traced surf flight (below) as segments at the crouch eye, and of the same flight lifted `crouch_lift` (stand eye). Rides: every eye piece of a reached `tops_only` node (the crouch and stand columns, the dead view, a fallback hull) swept to every pose its entity's pose links join: the hull of the piece at pose p and mapped to pose q, which is exact for a translation. For a rotating door (`func_door_rotating`, or an entity parented to one) the swing between two poses is one rotation about the hinge (the entity origin), moved Euler-linearly between the two poses' angles. It is cut into ceil(swing / (2 acos(1 - 1/r_max))) equal steps, at most 64, where r_max is the farthest vertex of the piece from the hinge, so a chord between two steps strays at most 1u from the arc; the hull of the piece at every step is then grown outward by r_max (1 - cos(step / 2)), which holds the whole swing. That moves each eye piece with the door, which is right only while world up does not tilt: a yaw-only swing (yaw is the outermost Euler rotation, about world z). A pitch or roll swing (spawnflag 64 or 128) instead sweeps the node's floor polygon the same way and hangs the whole eye column, dead view to top, world-up off every swept point, ignoring obstacles (over-reach): the rider's feet tilt with the floor, its eyes stay above them. Teleports: each triggered teleport's destinations, a segment from crouch to stand eye. Viewpoints (points): every `env_cubemap` sample of lump 42 (vbsp removes the entity), every `point_camera` and `point_viewcontrol` origin, and each `-viewpoint`.
- **3D skybox.** For every `sky_camera` (some maps switch between several; unverified, the engine source is not in this repo), every piece (viewpoints included) also goes in mapped by x -> origin + x / scale (planes: d -> n . origin + d / scale), for the eye clusters and the samples (sampled at spacing / scale, and fanned at fan spacing / scale, so a copy gets as many samples as the original). The sky_camera origin itself is a viewpoint: the engine's 3D skybox pass takes its PVS from there, I believe (`Draw3dSkyboxworld` -> `ViewSetupVis` with the sky camera origin; not checked against engine source here). That matches what the CS:S maps show: on cs_office, cs_italy and de_dust parts of the mapped eye volume lie inside the skybox room's solid, and the real world is not drawn in their skyboxes. So mapped pieces add their clusters (a superset) but never count as a camera in solid. Skybox faces are then seen only from mapped eyes and world faces only from real ones, with no special case: the two are sealed from each other.
- **Viewpoints in solid.** A viewpoint (env_cubemap, point_camera, point_viewcontrol, sky_camera, `-viewpoint`) that touches only solid leaves is a camera with no cluster, which has no PVS (the engine then draws every leaf). Every cluster becomes an eye cluster, with a warning: tier A proves nothing on that map. In tier B the viewpoint's own samples (`vis.solid_eyes`) keep the faces in front of them visible without a ray test: the eye sits inside the brush that would block every ray, while the engine draws through it (reason `no_eye`).
- **Dead eye.** A dead player's view sits `EYE_DEAD_HEIGHT` (14u, HL2's `VEC_DEAD_VIEWHEIGHT`) above the floor: each reached node also gets the prism from 14u to the crouch eye, which lies inside the crouch box on the floor and so needs no clip.
- **Sample count.** `-eyespacing` (default 8) is widened by 1.25x steps until the estimated sample count is at most `-eyemaxsamples` (default 24M; a sample takes 24 bytes, so 24M is about 576 MB), with a warning. The estimate covers every source: node columns (crouch, stand when `eye_stand` - `eye_crouch` needs its own column, dead view), ride sweeps, water and ladder volumes, ladder segments, arc and surf-flight chords, teleport segments and viewpoints. A solid piece counts about volume / s^3 + 2 xy-area / s^2 samples (plus its vertices), a segment length / s + 2, a point 1; the total is multiplied by (1 + the number of `sky_camera` entities). The gather briefly holds a second copy, so the peak is about 2 x 24 B x the samples made. The estimate tracks the kept (deduplicated) samples: on the 18 fixtures (2026-11-05) the kept count was 0.59 to 0.97 of the estimate and the samples made, before deduplication, were 1.18 to 1.47 times it. The console line prints both (`N made, M estimated`). de_dust (2026-11-04, when the estimate covered node columns only): 8u stayed, about 6M samples. A widened spacing weakens tier B (fewer eyes), so the JSON `vis` object records `eye_spacing_requested` and `eye_spacing_used` (equal when not widened); `bspwalk_runner.summary()` flags a difference (`[WARNING: ...]`), and `lmoptimizer.py` prints it on stderr. The older `eyes.spacing` is the used value.
- **Tier A** (needs vis data; without it a warning and every face goes to tier B). Faces map to clusters through every leaf that lists them (dleaffaces). A world face in no list (displacements, detail faces) takes the clusters its bounds (+0.5u) touch, a superset. The union of the PVS rows of the eye clusters is the seen set; a world face none of whose clusters is in it is tier A. Reflective faces (material shader `Water`, read from the VMT through `patch` includes, or texinfo `SURF_WARP`; any face of a `func_reflective_glass`) that are not tier A add their own clusters to the eye clusters, and the seen set is recomputed until nothing changes: a reflection is a camera at the mirror, so its view joins the proof. Visible reflective faces also add the clusters of their bounds mapped into each 3D skybox (a reflection shows the skybox too). Brush entity faces (models 1 and up) are never evaluated: always visible (`brush_entity`). A reflective one (`func_reflective_glass`) takes the clusters its bounds touch, because vbsp lists submodel faces only in the submodel's own leaves, which have no cluster (found in review: before that, reflective glass added nothing to either tier).
- **Tier B occluders** are the opaque solid brushes only: world brushes and the world-like `func_brush` (`CAT_FUNC_BRUSH_SOLID`) whose contents have `CONTENTS_SOLID` and none of `WINDOW`, `GRATE`, `TRANSLUCENT`, `WATER`, `SLIME`, shrunk 1/32u. vbsp already strips `SOLID` from any brush with a non-opaque material (`textures.cpp`, `map.cpp BrushContents`), so this needs no material check, and packed custom materials are covered the same way. A world brush whose every side is nodraw (none sky; sky sides count as drawn) draws nothing and does not occlude, and neither does one with a nodraw side (not sky) that borders the map's open space: a ray can enter the brush through that side, where the engine draws nothing, and the drawn side it leaves by faces away from the eye. A nodraw side against another brush or the void (a solid leaf, cluster -1, 1/8u out) is not open. A world-like `func_brush` (Stage 3) occludes only when it is also drawn opaque all game long: `rendermode` 0, `renderamt` unset or 255, `renderfx` 0, no `EF_NODRAW` effect, no `fademaxdist`, none of `mindxlevel`, `maxdxlevel`, `mincpulevel`, `maxcpulevel`, `mingpulevel` or `maxgpulevel` set, no nodraw side at all (its planes are in model space, so the open-space test cannot run), and it is not the target (by name, with a trailing `*` wildcard, or `!self` from its own output) of an output that sends `Disable`, `Toggle`, `Kill`, `KillHierarchy`, `Alpha`, `AddOutput`, `DisableDraw`, `SetParent`, `SetParentAttachment`, `SetParentAttachmentMaintainOffset`, `SetRenderMode` or `SetRenderFX`. Both output separators (`,` and 0x1B) are read. One such output aimed at `!activator`, `!caller` or `!picker` (an entity known only at run time) stops every `func_brush` from occluding. Playerclip, water, props and every other brush entity do not occlude. A segment is blocked only where it runs more than 1e-6u inside an occluder (touching, and running along a face, are free; selftest (h6)). BVH over the occluder boxes.
- **Tier B passes** (CPU reference, multithreaded). 1. *Fan*: one eye per `-fanspacing` cell (default 64) shoots `-fanrays` (default 1024) Fibonacci-sphere rays; each ray marks every face it crosses (front side; either side of a two-sided face: `$nocull` or water) up to 0.05u past its first occluder. 2. *Face pass*, for every face the fan missed: samples on a grid `-facespacing` apart (default 4u, any positive value: a larger one samples faces more coarsely and can leave tier B a face a finer grid sees; coarser by doubling past 2^18 samples a face; JSON `vis.face_spacing` is the requested value, `vis.faces_spacing_widened` the faces that got a coarser grid and `vis.face_spacing_used_max` the widest grid used), edges inset 1/16u, plus the inset vertices, edge midpoints and the centroid, lifted 1/256u; displacements are sampled per render triangle. The candidate eyes are the samples in clusters whose PVS row holds one of the face's clusters, in front of its plane (not culled for two-sided faces and displacements), at most 65,536 of them (an even stride beyond; the finest default bin level uses 4,096 per tile). Samples are grouped in 32u cubes; per cube, one eye per octahedral bin (`-eyebins`^2, default 32^2, the nearest), and a cube that finds no clear ray tries again with twice the bins over the eyes it has not tried, up to `-eyebinlevels` (default 2) levels. Any clear sample-to-eye segment makes the face visible (`ray`). 3. *Mirrors*: for each reflective face R that is not tier A, the candidate eyes in front of it are mirrored in its plane; a face with some part in front of R is sampled the same way against the mirrored eyes, and a path counts when the segment to the mirrored eye crosses R's plane inside R's polygon (1e-2u outward tolerance) at Q, and both sample -> Q and Q -> the real eye are clear (`mirror`). Selftest (h7, h8): f16's mirror point, the Fibonacci set, distinct octahedral bins. A face no pass reaches is tier B (`rays`).
- **Faces kept visible without a ray test (`no_eye`).** A face the fan did not mark stays visible, with reason `no_eye`, when no ray test can speak for it (`FacePassOne` in `bw_vis.cpp`): (1) it has no sample point; (2) it is in the PVS of a bare eye cluster (with no vis data any bare cluster counts) and part of that cluster's box of eye piece parts lies in front of the face's plane (any part, for a two-sided face or a displacement); (3) a viewpoint sample in a solid leaf lies in front of it (any such sample, for a two-sided face or a displacement; the eye sits inside the brush that would block every ray); (4) in the mirror pass, a reflective face R that is not tier A meets (2) or (3) and part of the face lies in front of R, since R shows it. `vis.visible_noeye` counts these faces, `vis.noeye_clusters` the bare clusters and `vis.solid_eyes` the viewpoint samples in solid. Under `-notierb` no face gets this reason (every face the PVS does not hide stays visible as `no_tierb`).
- **GPU face and mirror passes.** A straight segment a -> b is an arc of the existing kernel (`bw_arcs.cu`, unchanged): o = a, v = b - a, `dg0` = -gravity (so the arc's gravity is exactly 0 in float), `tEnd` 1, one chord. The occluders (the shrunk opaque brushes, rebuilt from their planes and fan-triangulated) are a third mesh, `BW_MESH_VIS`, with its own GAS. In the face pass each 32u tile at each bin level packs every (sample, eye) pair that passes the back-face test into one launch (a mirror pair is two segments, both of which must be clear), so the GPU loses the CPU's early exit inside a tile level but keeps it between them; launches are serialized by a mutex across the worker threads. A failed launch traces that batch on the CPU. The JSON's `vis.path` is `gpu`, `gpusim` (`-visgpusim`) or `cpu` (`-cpuvis`, no GPU path, or `-notierb`, where no face pass runs); `vis.mesh_tris` the occluder triangles. `-cpuvis` stays on the CPU. `-vischeck` traces every packed segment on both paths, decides with the CPU and reports `vis.check` (`segments`, `gpu_only_blocked`, `cpu_only_blocked`, `tile_levels_differ`); it never changes the exit code. `-visgpusim` runs the GPU path's batching with each packed (float) segment traced on the CPU, which tests the host side without a GPU: the 17 fixtures then built passed identically under it (2026-11-04; f16: 1.84M segments). With `-vischeck` it compares the CPU with itself, so its console line says so and reports nothing. How the grow is exact (`bw_grow.cpp`): candidate normals are the source face normals, the 6 axes and ±edge×axis for every edge. A candidate is a facet when its support set (source vertices and box corners attaining the max) spans 2-D. Facets are deduplicated by support set, never by near-equal normals: two real edges 1e-7 rad apart give two real facets, and merging them overgrew a fightspace3 prop by 0.001u. Each face polygon is the 2-D hull of its support set's sum points, so every vertex is an exact `v + c` and no plane intersections are computed. Clipping nearly parallel planes (ChopWinding) put vertices up to 1e-3u off. ChopWinding (double port) still builds the brush convexes from their planes. Prop convexes are rebuilt as the hull of their vphysics points, because vphysics' float triangulation of "planar" quads is bent and its diagonals need not be hull edges (a missing edge dropped a facet and overgrew a crate by 4.5u). The grow works on the hull of the source points (quickhull), because brush windings clipped from float planes are convex only to about 1e-4u. Candidates also include the face normals of the hull of the sum points, a safety net for the micro-chamfers that float brush planes leave. An extra candidate is always safe: its offset is the exact support, so it can only remove overgrowth. Support sets use a tolerance of 1e-9·|coord| + 2e-6. Measured overgrowth (the distance from a plane-intersection corner to the sum hull) on fightspace3 is at most 2.3e-4u, at |coord| 13316, which is below half a float ulp of the coordinates there. The 16 fixtures and all other fightspace3 convexes are within 1e-8·|coord| + 1e-5. The planned 1/32u shrink (Stage 2) absorbs it.

For #13: the grown planes include near-coplanar pairs, which come from source faces tilted by float error (6.5e-5 rad apart on convex 371). Their intersection lines cross faces far from any real vertex: on fightspace3 convex 371, one corner is 1176u from every sum point but only 4e-5u outside the hull. Use the face polygons, whose vertices are exact sum points, or the planes as half-spaces. Never derive vertices by intersecting plane triples.

## Stage 2: walkable surfaces (exact, no grid)

The feet can rest on the upward faces (normal z ≥ 0.7) of grown polytopes. For each such face:
1. Clip away the parts inside any other grown polytope of the same posture. The spatial index is a uniform hash on polytope AABBs.
2. What remains is a set of convex polygons where the box fits standing (repeat crouched for crouch-only floor).
3. Split polygons larger than 64u so graph edges stay local.

A 32.01u corridor gives a 0.01u-wide polygon, so slivers are kept exactly. Any epsilon must be in the safe direction: shrink grown solids by 1/32u, never grow them.

Water volumes (CONTENTS_WATER leaves): all free C-space inside them is reachable, with free vertical movement. Ladders (`func_useableladder` segments, `func_ladder` and CONTENTS_LADDER volumes): the climbable volume is reachable and connects to the walkable polygons at its ends.

## Stage 3: movement graph and flood

Nodes are walkable polygons plus water and ladder volumes. Edges:
- **Walk/step:** polygons whose boundaries are within step height (18u) and touch in XY, with the connecting segment free in C-space. Exact, on the CPU.
- **Fall and jump:** ballistic arcs on the GPU (OptiX). As built in #13 they are target-driven pairs from the flood frontier, not a direction fan (see "How #13 arcs work"). The original plan was launches from samples along polygon edges and interiors, for a direction fan and a speed set up to the profile's max ground speed, standing and crouch-jump. Each arc is traced as short segments, as rays against the grown-solid triangle mesh, so the point trace is an exact box trace. A landing on another polygon adds an edge. Arc samples also feed the eye volume (Stage 4).
- **Teleports:** a `trigger_teleport` whose volume intersects reached C-space seeds its target entity's origin. A `point_teleport` is seeded unconditionally at its own origin (JSON seed `source` `point_teleport`) when it can move the player: its `target` is a `!` name other than `!self` (`!player`, `!activator`, `!caller`, `!picker`, ...), or names no entity in the BSP (a trailing `*` matches as the engine does), since the player is not in the BSP. A `target` that names a BSP entity (an NPC, a prop) skips it: that entity is moved, not the player. So does an empty `target`. Whether its `Teleport` input is ever fired is not checked (over-reach). With spawnflag 1 the destination is the target's spawn position, not the origin, so the origin seed is then pure over-reach.
- **Brush entities other than `func_brush`** (`func_door`, `func_door_rotating`, `func_movelinear`, `func_tracktrain`, `func_tanktrain`, `func_breakable`, `func_physbox`, `func_rotating`, …), the "tops only" rule (user decision 2026-11-02):
  - *Player-solid check first.* Skip the entity entirely if its brushes' contents miss the player mask, or a spawnflag makes it passable (e.g. `func_door` "Passable", `func_illusionary`, `func_clip_vphysics`).
  - *Sides do not exist.* A solid mover contributes **no** C-space obstacle; doors are assumed openable. A permanently locked door used as a wall makes the flood over-reach, which is the safe direction: it costs savings, never blacks a face.
  - *Tops are floors.* Its upward faces (normal z ≥ 0.7) become walkable-polygon candidates, clipped against world solids for headroom, at every pose it can hold: spawn; open (`func_door` via movedir + lip, `func_door_rotating` at its open angle); start/end (`func_movelinear`); each `path_track` (trains).
  - *Ride edges.* Consecutive poses connect, and boarding edges (18u step) connect a pose to reached ground. The swept volume between poses feeds the eye volume. Riding a top is the only way a mover relocates the player; being pushed by one is ignored, since the player can walk that ground anyway. Vertical `func_door` elevators fall out of this automatically.
  - *Never occludes sight.*
- **`func_brush`** gets its own cases, because it is toggleable and parentable:
  - `Solidity` = Never Solid → ignored.
  - Unparented, `Solidity` = Always Solid, not `StartDisabled`, never the target of an input that can turn it off, remove, move or rekey it (`Disable`, `Toggle`, `Kill`, `KillHierarchy`, `AddOutput`, `SetParent`, `SetParentAttachment`, `SetParentAttachmentMaintainOffset`; by name, trailing `*` wildcard allowed; both output separators read; also from its own `!self` outputs, and none at all while any output sends one of them to `!activator`, `!caller` or `!picker`) → treated as world: full obstacle.
  - It is also an occluder only when it is drawn opaque all game long, a stricter test than the obstacle rule: any input that can hide, remove, make translucent, move or rekey it (`Disable`, `Toggle`, `Kill`, `KillHierarchy`, `Alpha`, `AddOutput`, `DisableDraw`, `SetParent`, `SetParentAttachment`, `SetParentAttachmentMaintainOffset`, `SetRenderMode`, `SetRenderFX`), also from its own outputs (`!self`), takes it out; so does any such output aimed at `!activator`, `!caller` or `!picker` (for every `func_brush`), and so do render-state, fade and level keys (`rendermode`, `renderamt`, `renderfx`, `effects`, `fademaxdist`, `mindxlevel` and the other level keys) and any nodraw side. The exact list is under "Tier B occluders".
  - Toggleable or `StartDisabled` → tops only, like a mover, and no occlusion (it may be invisible).
  - Parented (`parentname` set) → tops only, at the parent's poses if the parent is a mover (train or door), else spawn pose. No occlusion.
- Per-classname overrides on the CLI for all of the above.
- **Pushes:** `trigger_push`, `trigger_catapult`, `func_conveyor`, `trigger_wind`. Reached C-space inside the volume launches arcs with the push velocity added (catapult: its target trajectory). The landings become edges.
- **Ladder jump-off:** every ladder volume also launches jump arcs along its length, not only at its ends.
- **Steep slopes** (normal z < 0.7): an arc landing on one continues as a slide down the slope, traced the same way. Slide samples feed the eye volume and the slide's end is a landing.
- **Vehicles** (`prop_vehicle_*`): driving is not simulated. Their spawn origins are always seeds (policy), and `-vehicle-free` additionally treats the ground connected to a vehicle spawn as reached in both directions (as built: see "How #13 special movement works").
- **Dynamic prop stacking** (piling crates to climb): not modelled; accepted limitation.
- **Seeds:** all `info_player_*`, `info_ladder_dismount`, `prop_vehicle_*`, the `point_teleport` origins above, CLI `-seed x y z`. Zero seeds is a hard error, never an empty result.

Flood with a BFS over the graph. Output: the reached node set and an unreached-but-walkable report, which shows mappers where the sim thinks players can't go.

**Game profile** (`game/bin/x64/bspwalk_profiles.txt`, KeyValues; as built: `half_width`, `stand_height`, `crouch_height`, `eye_stand`, `eye_crouch`, `step_height`, `gravity`, `jump_velocity`, `crouch_lift`, `run_speed`, `max_ground_speed`, `max_air_speed`, `reach_margin`, `air_jumps` 0 or 1, `arc_max_drop` (the deepest fall whose XY reach arcs are tried at), `gamedirs`; `maxJumpRise` and R(drop) are derived; cstrike and tf values are marked unverified): hull sizes, eye heights (64/28), step 18, gravity, jump impulse, crouch-jump bonus, max ground speed per game/class, and a `reach_margin` multiplier (default 1.15) that deliberately over-estimates reach. Over-reach only costs savings; under-reach blacks out faces. The margin hedges physics-constant error **only**. Bhop and air-strafe accelerate past ground speed, so the profile carries a separate `max_air_speed` per game (its bhop/air-strafe ceiling where the game caps it; a generous default, 2× run speed, where it doesn't). The arc speed set runs up to that. Routes beyond it are an accepted limitation; the unreached-but-walkable report is where they show up. Profiles: hl2, episodic, cstrike, tf (max class speed), hl2mp. The default is chosen from the gameinfo.

## Stage 4: eye volume

For each reached walkable polygon, the eye volume is the prism over it from feet+eye_crouch up to feet+eye_crouch+rise, with rise = max(max_jump_rise, jump_apex*(1+air_jumps)+eye_stand-eye_crouch) (hl2: 85.33 above the feet), clipped to free space (see "Node columns"). Add the jump/fall arc samples from Stage 3, and water/ladder volumes offset by eye height.

**3D skybox:** if `sky_camera` exists, every eye point maps into the skybox (`sky_origin + eye / scale`). Skybox faces are evaluated from those mapped eyes, never from reachability.

**Extra viewpoints** always added: `point_camera` origins (monitors), `env_cubemap` origins (cubemaps are captured from there, independent of the player), and any `-viewpoint` from the CLI.

**Second cameras:** water reflection/refraction and `func_reflective_glass` render from mirrored origins outside the eye volume. Any reflective surface whose face is visible (or unproven) is treated as an eye-volume cluster for **both tiers**. Its cluster's PVS joins the tier A set, and its mirrored eye points join the tier B eye set. Without that, tier A would not be a proof on maps with reflective water.

## Stage 5: visibility, tiered by proof strength

Occluders: the shrunk (1/32u) convex volumes of opaque brushes. That means `CONTENTS_SOLID` world brushes whose contents have none of window, grate, translucent, water or slime (vbsp already strips `SOLID` from a brush with a non-opaque material). A brush whose every side is nodraw (none sky) draws nothing and is left out, and so is a world brush with a nodraw side that borders open space; the full rules are under "Tier B occluders" in "How #14 visibility works". Props never occlude (`-propocclude` is not built). Brush entities do not occlude, except a world-like `func_brush` (Stage 3 policy) that is also drawn opaque all game long.

- **Tier A, PVS-proven hidden:** a face whose leaves (from `dleaffaces`, *all* of them, not the centroid's) are in no cluster of the PVS of any cluster the eye volume touches. VVIS PVS is a conservative superset (even `-fast` falls back to the looser portal flood), and areaportals only ever close visibility. So this is a proof given a correct eye volume, including the second-camera clusters and extra viewpoints from Stage 4. Requires VVIS data; without it tier A is empty and the tool says so.
- **Tier B, ray-tested hidden:** three passes over the rest (details under "Tier B passes"): a fan on the CPU, then the face and mirror passes, which run on the GPU by default (`-cpuvis` is the CPU reference).
  1. *Eye-driven (CPU):* one eye per `-fanspacing` cell (default 64u; the cell is a spatial key over x, y and z, and a skybox copy has its own cells at spacing / scale, kept apart from the real ones) shoots `-fanrays` (default 1024) Fibonacci-sphere rays; each ray marks the faces it crosses, up to 0.05u past its first occluder, as visible. Cheap, and clears most faces.
  2. *Face-driven:* for each face still unmarked, sample its area on a grid `-facespacing` apart (default 4u, no cap; edges inset 1/16u) and trace to eye points in PVS-visible clusters, chosen by angular binning, not by truncating a distance-sorted list: per 32u cube of samples, one eye per octahedral bin (the octahedral map is not equal-area, so bins differ in solid angle), and a retry at twice the bins when no ray is clear. Any clear ray means visible.
  3. *Mirrors:* the same against the eyes mirrored in each reflective face that is not tier A.
  Whatever survives is tier B. A face no ray test can speak for stays visible (`no_eye`, see "Faces kept visible without a ray test").
- **Visible:** everything else.

**Output policy, the key safety lever (decided in #16):** every hidden face, tier A or tier B, gets the maximum lightmap scale, never nodraw. A sampling miss then renders blurry, never black, and the face keeps bouncing light (nodraw would darken lit areas next to it). Which tiers the optimizer acts on is in Decisions below.

## Decisions (owner: user; #16, closed 2026-11-05)

- Tier output: every hidden face gets max lightmap scale, never nodraw. Nodraw is not offered; build it only on request, since it kills bounce light next to the face. The optimizer's `--bspwalk-tiers` defaults to `A` (PVS-proven only) while #25 (tier B marks large visible faces hidden) is open; switch the default back to `A,B` when #25 closes. `vis_simulator.py` keeps `A,B`, because it is the tool for inspecting tier B.
- Movers (2026-11-02): tops only for all brush entities except `func_brush`, which has its own cases (Stage 3).
- Game profiles: all five ship in `bspwalk_profiles.txt`. hl2 and episodic are the checked ones (SDK 2013 values, fixtures). hl2mp shares the SDK values but is not fixture-tested. cstrike and tf are unverified until each runs on a real map.
- VVIS is required for tier A; no internal portal flood fallback. In auto-compile mode the optimizer refuses to run without VVIS (the baseline needs it for bounce light); with `--bsp` it only warns, and an unvis'd BSP then gets no tier A, so with the default `A` nothing is hidden. Even `vvis -fast` gives a conservative PVS, so a second visibility system would only serve standalone bspwalk runs on unvis'd maps, which still get tier B.
