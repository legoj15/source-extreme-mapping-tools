# Agent notes

More rules live in `.agents/rules/` and workflows in `.agents/workflows/`.

## Layout of game/bin/x64

The top level holds only the tool binaries (exe, dll, pdb, ptx) and `bspwalk_profiles.txt`. Everything else is in folders: `scripts/` (command-line tools), `scripts/lib/` (modules that are only imported), `gui/` (`lmoptimizer_gui.py` and its `.bat` launcher), `tests/` (the suites, `tests/maps` and `tests/compare/maps` fixture maps, the CPU-vs-GPU comparison in `tests/compare`, double-click `.bat` launchers, and git-ignored run output in `tests/out`). The tools load their PTX from the working directory, so run them with `game/bin/x64` as the cwd.
A Python file that needs one of these folders imports `binpaths` (in `scripts/lib`: BIN, SCRIPTS, LIB, GUI, TESTS, TESTS_OUT, REPO, `exe(name)`) instead of counting `..` from its own file. Entry points run under `python -I`, which drops the script's folder from `sys.path`, so each starts with the same one-line preamble that sets `sys.path[:0]` to `scripts/lib` and `scripts`; copy it from a neighbour, and grep for `sys.path[:0]` to list them all.

## Scripts

- `bash .agents/scripts/run_suites.sh [--only a,b]`: the quick regression suites (bspwalk selftest, fixtures and eye cache, lmoptimizer, proplm, vvis sight-line and mergeflow) against the binaries in `game/bin/x64`, one pass/fail line each; `--only` also takes the opt-in suites `compare_vrad` and `compare_vvis` (`run_compare_tests.ps1 -Tool vrad|vvis -Group core`, see below), which are not in the default run because they need the SDK reference binaries and the SDK game dir. Run it after a merge or a rebuild (`game/bin/x64/tests/run_suites.bat` is the double-click launcher). `bspwalk_cache` (`game/bin/x64/tests/bspwalk/run_bspwalk_cache_tests.py`) reads the fixture BSPs `bspwalk_fixtures` compiles: it runs `-eyeverify` on each at every `-eyerefine` level (`-eyeverify` makes every tile: it is the complete check of the cluster tile lists and of each tile's piece gathering), and requires the same tiers at the default eye cache, `-eyecache 1`, `-threads 4` and `BSPWALK_FACE_BATCH=1` on four of them, and on f11 and f17 at `-eyespacing 2` (faces past the candidate cap: the thinning and the sweep); run it after any change to the eye store or the tile generator (`bw_eyestore.cpp`, `bw_eyes.cpp`).
- `pwsh game/bin/x64/tests/compare/run_compare_tests.ps1 -Tool vrad|vvis (-All | -Group <g> | -TestNames a,b) [-SkipVisualCheck] [-TimeoutExtensionMinutes N]`: the three-way comparison of the SDK's reference `vrad.exe` / `vvis.exe`, our CPU leg and our GPU (vrad) or all-threads (vvis) leg, one `compare_harness.ps1` run per test in `vrad_tests.psd1` / `vvis_tests.psd1` (the shared flow is in the harness; the per-tool steps are the `Invoke-Vrad*` and `Invoke-Vvis*` functions). Lightmap and screenshot comparisons go through `tests/compare/image_compare.py` (`lightmaps`, `ssim`, `tga2png`; `ssim` needs numpy, opencv-python and Pillow). Needs SDK Base 2013 MP at the path in the harness. Double-click launchers: `tests/test_vrad.bat`, `tests/test_vvis.bat`. The vvis tests are named for their map: `fightspace3` and `trainstation_02` (group `production`).
- `pwsh game/bin/x64/tests/compare/vrad_noise_floor.ps1 (-All | -Group <g> | -TestNames a,b) [-Runs 2] [-OutDir <dir>] [-BinDir <dir>] [-SkipRef] [-Threads N] [-CompareOnly]`: measures the lightmap noise floor behind the `RefCpuLightmapThreshold` and `CpuGpuLightmapThreshold` values of `vrad_tests.psd1`: it compiles each selected map once with the SDK install's `vrad.exe` and `-Runs` times with `vrad_rtx.exe` on the CPU and with `-cuda`, interleaved, into `tests/out/vrad_noise_floor/<test>/<leg>/`, then prints (and writes to `tests/out/vrad_noise_floor/noise_floor.csv`) one row per test: the largest `image_compare.py lightmaps` figure between two cpu and between two gpu runs (the noise floor), the smallest..largest between the reference and each cpu run and between every cpu and gpu run (percent of the decoded light, four decimals, `structural` when the lit faces differ), the two current thresholds and the mean run times. It only measures (no figure is judged, `vrad_tests.psd1` is not touched; exit 1 only when a test could not be measured); use it before changing a threshold. `-CompareOnly` compiles nothing and rebuilds the table from the BSPs of the last run with the same `-Runs` and `-OutDir` (for after a change to `image_compare.py`).
- `python -I game/bin/x64/scripts/bsp_lumps.py diff a.bsp b.bsp`, or `repro MAP.vmf --game <dir> --out <dir> [--rounds N] [--variant "-threads 1"]... [--vbsp EXE] [--keep]`: `diff` compares two BSPs lump by lump (game lumps one by one, then the whole file; exit 0 identical); `repro` compiles one VMF repeatedly with `vbsp_lmo` (variants interleaved) and checks every BSP and `.prt` against the first. The VBSP reproducibility and threaded-block-pass check.
- `python -I .agents/scripts/proplm_rebake_ab.py [--vbsp A.exe --vbsp B.exe] [--keep DIR] model...`: compiles the staticpropbounce fixture with one `proplm "rebake"` prop per model and prints the rebake log lines and the pak files it added (sizes, CRC); with two VBSP builds it diffs the pak lumps. A second build must sit in `game/bin/x64` (it needs the DLLs beside it).
- `bash .agents/scripts/worktree_build_setup.sh [--build] [--project <name>]...`: makes a fresh git worktree buildable (copies the untracked libs, runtime DLLs and test maps from the main checkout, generates the projects, fixes the solution name), then builds the whole solution or only `src/utils/<name>`. Run it first in any new worktree, and again after a `.vpc` changes.
- `bash .agents/scripts/review_extract.sh <out_dir> <base> <head> <regex>...`: a small two-commit repo of just the files a third-party review needs. Point `review_fast` / `review_final` at it (`diff_range xbase..xhead`); the full repository snapshot is too large to launch.
- `bash .agents/scripts/ladder_extract.sh make <out_dir> <regex>...`, then from the extract or any worktree of it `build [worktree_build_setup.sh args]`, `run '<command line>'` and `where`: the host check for a `ladder-implement` run whose `repo` is an extract (the whole repository is too large for the container and the review hosts, and an extract cannot be built). `make` is `review_extract.sh <out_dir> HEAD HEAD <regex>...` plus `extract.source` (this repository) and `extract.base` (HEAD) in the extract's git config, which every worktree of the extract shares. `build` makes the sibling worktree `<extract worktree>-real` of the main repository at the base, brings it to base plus the extract worktree's change (`git diff xbase`, untracked files included; the patch an earlier build applied is reverse-applied first, so nothing else in that worktree is touched), then runs `worktree_build_setup.sh` there with the same arguments (none: inputs and projects only; `--project vbsp`: also builds it). `run` runs a command line with bash from the top of that worktree, `where` prints its path. Exit 3: the change does not apply. Give `ladder-implement` the extract as `repo`, `bash "<main checkout>/.agents/scripts/ladder_extract.sh" build --project <name>` as `build` and `bash "<main checkout>/.agents/scripts/ladder_extract.sh" run '<check>'` as `check` (the absolute path to the script in the main checkout, because an extract usually does not contain `.agents/`). Remove the pair when done: `git -C <main checkout> worktree remove --force <extract worktree>-real`. The first `build` of a pair takes minutes on a busy box (it copies the untracked test maps and generates the projects), more than `ladder-implement`'s 260 s command limit: for a C++ change run `implement_single` on the extract yourself, then `build` and `run` in the background, instead of going through the workflow.
- `python game/bin/x64/scripts/prop_corpus_check.py --game <dir>`: feeds every model the game mounts through VBSP's `prop_static` path and lists the ones it refuses, with the reason. Run it after any change to the model checks (`Proplm_ValidateMdl`, `Proplm_LoadVvdVertices`, `LoadStudioModel`); about 15 seconds for stock HL2 content.
- `python -I .agents/scripts/proplm_ppl_ab.py --game <dir> --out <dir> --vrad old=<bin dir> --vrad new=<bin dir> [--lights 3000] [--coverage] model[:plain]...`: compiles the staticpropbounce fixture once, runs each VRAD build on it with `-StaticPropLighting`, and compares the per-texel prop lightmaps (`texelslighting_N.ppl`): texels lit only in one build, difference on the common ones, and (labelling one build twice) the run-to-run noise floor; `--coverage` re-derives VRAD's lit-texel counts from the rebaked model. Needs numpy. Use it for any change under the per-texel prop lighting in `vradstaticprops.cpp`.
- `python -I .agents/scripts/proplm_ingame_check.py --sdk <SDK 2013 MP root> --mod <mod dir> --out <dir> --label <name> [--vbsp-args "..."] [--mark-b rebake|none] [--fullbright --no-static-prop-lighting] [--lod N] model[:camera distance]...`: compiles a two-room map (room A plain props, room B the same props marked `proplm "rebake"`), runs it on the SDK 2013 MP engine and saves one screenshot per prop per room. The SDK ships no game DLLs: `--mod` is a mod folder whose gameinfo mounts the SDK's hl2mp content with `game+mod` on its own folder and whose `bin/x64` holds HL2DM's client.dll and server.dll. Use it for any change to what a static prop's lighting or model looks like in game.
- `python -I .agents/scripts/renamed_model_check.py --sdk <SDK root> --source-vpk <vpk> --out <dir> --vbsp base=<exe> --vbsp new=<exe> --vrad old=<bin dir> --vrad new=<bin dir> [--layout original]`: builds a scratch copy of the SDK's hl2mp game dir (junctions, hardlinks, nothing written to the install) holding one stock static prop copied byte for byte under another file name, then reports every VBSP and VRAD build's exit code and message on it (`--layout original` is the control with the file name unchanged).
- `python -I .agents/scripts/proplm_stale_vtf_check.py --game <dir> --out <dir> --vbsp base=<exe> --vbsp new=<exe>`: seeds a two-`proplm "1"`-prop map through VBSP and VRAD, then drops props from the VMF and recompiles with `-onlyents` (and `-keepstalezip`), listing the `materials/maps/<map>/proplm/<id>.vtf` pak entries before and after.
- `python -I .agents/scripts/vvis_pvs_compare.py --maps <dir> --out <dir> --run base=<bin dir> --run new=<bin dir>[,args]`: runs vvis builds (or edited portal files, `label=<bin dir>@<prt dir>`) on copies of the same BSP+PRT pairs and says whether the visibility lump is byte-identical, listing the cluster pairs gained and lost when it is not. Use it for any change under `src/utils/vvis`.
- `python -I .agents/scripts/vis_row_merge_stats.py <bsp> [--prt <prt>] [--tol 0,0.01,...] [--adjacent-only]`: what merging clusters with identical or near-identical PVS rows would do to a vis'd BSP: clusters, vis lump bytes and visible leaf pairs per tolerance. Needs numpy. Results and the decision are in `docs/visclusters.md`.
- `python -I .agents/scripts/blockgrid_sweep.py --game <dir> --out <dir> --variant 1024= --variant "2048=-blocksize 2048" [--vis=-mergeflow] [--strip-visclusters] [--reuse | --remeasure] map.vmf...`: compiles each map once per VBSP block-grid variant, runs vvis, and prints per map the clusters, vis time and what a player on the floor has in the PVS (share of the floor, world triangles, static props; `game/bin/x64/scripts/pvs_cost.py`). Use it for any block-grid question (`-blocksize`, `-blockoffset`, a default). Compare a size at several `-blockoffset` positions before believing a difference of a few percent, and never judge vis time from one grid position.
- `python -I .agents/scripts/make_corridor_prt.py <out_dir> <clusters>`: a synthetic straight-corridor portal file for a portal chain of a known depth (vvis's depth check).
- `python -I game/bin/x64/scripts/bspwalk_view.py --bsp <map.bsp> --game <dir> [--vmf <map.vmf>] [--faces 437,17128] [--sides 113898] [--out view.html] [--keep DIR | --reuse DIR]`: why bspwalk marked a face visible, in 3D. Runs bspwalk twice (`-traceface` with `-tracejson`, then `-traceeye` at each witness eye) and writes one HTML page the user opens locally: the map coloured by tier and reason, Hammer-like fly and orbit, click a face for its face, side and brush ids, and for a traced face the witness ray, its eye and eye piece, and the walk chain to the seed. Use it to answer "why is side X visible"; the BSP needs `-emitsideids`. `--reuse` rebuilds the page from a `--keep` folder in seconds.
- `python -I .agents/scripts/bspwalk_tier_diff.py base.json other.json...`, or `--bsp <map> --game <dir> --out <dir> --run base=<bin dir> --run new=<bin dir>[,arg...]`: diffs bspwalk face tiers between `-out` files, or runs several builds or argument sets on one BSP and diffs them (faces hidden in one run only, eye spacing and sample count, stage times, peak memory). `--same` exits 2 unless the tiers match. Use it for any change to the eye volume or the tier B passes (`bw_eyes.cpp`, `bw_vis.cpp`).
- `python -I .agents/scripts/hidden_face_savings.py --bsp MAP.bsp --walk WALK.json [--json OUT.json]`: what an opt-in compile pass that drops the faces bspwalk found no eye for would save (issue #102; tier A is proven from the vis data, tier B is a search that found no sight line): for all faces, the hidden ones together and each hidden tier, the face, triangle and lightmap counts (luxels and lighting-lump bytes, the LDR and HDR lumps each when both exist), a BSP size estimate (face and original-face entries, lighting bytes and the surfedges only the hidden faces use, with the edges and vertexes only they use reported separately), the hidden faces' share of the lightmap samples VRAD lights as a VRAD work proxy (not a timing) and the ten hidden faces with the most luxels. Use it with a bspwalk `-out` JSON and the lit BSP it was made from when weighing that pass's savings against its risk; it only measures, nothing is removed.

## Testing tools

Always pass `-game <dir>` when running any tool here (vbsp_lmo, vvis_optix, vrad, bspwalk) in a test, harness or script. Without it the tools fall back to the `VPROJECT` environment variable, which on a dev box can point at an unrelated game. The result is missing models or a vphysics.dll load failure that looks like a DLL problem. The bspwalk fixture harness's default game is set in `game/bin/x64/tests/bspwalk/run_bspwalk_tests.py` (`--game`).
